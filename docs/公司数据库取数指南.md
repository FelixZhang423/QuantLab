## 0. 连接信息

| 项 | 值 |
|---|---|
| ClickHouse HTTP 接口 | `<公司ClickHouse地址>` |
| 账号 / 密码 | `<用户名>` / `<密码>` |
| 网络要求 | 公司网络环境 |
| 客户端 | 无需安装 clickhouse-client，Git Bash 自带的 curl 就够 |

所有命令的骨架（下面全是它的变体）：

```bash
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000" --data-binary "<SQL>"
```

`max_memory_usage=1000000000` 是公司笔记里给的 1GB 内存上限，建议每次都带上。

## 1. 三种查询方式

### 1.1 一条命令直接带 SQL（最常用）

```bash
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000" \
  --data-binary "SELECT version(), currentUser()"
```

### 1.2 交互式输入（`--data-binary @-`，即你笔记里的方式）

```bash
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000" --data-binary @-
# 然后粘贴 SQL，例如：
describe table dws.f10_derivative_index_fd;
# 结束输入（会触发执行）：
#   Git Bash / Linux / macOS → 按 Ctrl+D
#   Windows cmd / PowerShell → 按 Ctrl+Z 再按回车
```

注意：**Ctrl+Z 只在 cmd/PowerShell 里是"结束输入"；在 Git Bash 里 Ctrl+Z 是"挂起进程"**（命令停住但不执行），Git Bash 用户按 Ctrl+D。

### 1.3 SQL 存成文件再执行（含中文条件时必须用这个）

```bash
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000" --data-binary @query.sql
```

`query.sql` 用 UTF-8 保存，内容就是一条或多条 SQL。

## 2. 中文条件的编码坑（实测，必读）

同一条查询、同一个库，只因为中文写的位置不同，结果完全不同：

| 写法 | 实测结果 |
|---|---|
| 中文直接写在命令行里：`--data-binary "SELECT ... WHERE type = '研报'"` | **返回 0 行**（参数被转成 GBK，服务端按 UTF-8 匹配不上） |
| 中文写在 .sql 文件里：`--data-binary @query.sql` | **返回 664,801 行** ✅ |

两个解法（都实测有效）：

1. **含中文的查询一律走 1.3 的 @文件方式**（推荐，简单稳妥）
2. 或用 `unhex` 代替中文字面量：`WHERE type = unhex('E7A094E68AA5')`（`研报` 的 UTF-8 十六进制）

## 3. 输出格式与导出

| 需求 | 做法 |
|---|---|
| 屏幕查看 | 默认制表符输出；加 `FORMAT TSVWithNames` 带表头 |
| 导出 CSV（带表头，Excel 可开） | SQL 末尾加 `FORMAT CSVWithNames`，命令加 `-o 文件名.csv` |
| 导出制表符格式（QuantLab 用的就是这种） | `FORMAT TabSeparatedWithNames` |
| JSON | `FORMAT JSONEachRow` |
| 限制内存/超时 | URL 参数 `?max_memory_usage=1000000000&max_execution_time=1800`（秒） |

导出单日数据（实测通过）：

```bash
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000" \
  --data-binary "SELECT code, timestamps, open, close, high, low, vol, amount FROM dws.ll_stock_daily_sharing WHERE category = 'stock' AND timestamps = '2026-10-09' ORDER BY code FORMAT CSVWithNames" \
  -o 20261009.csv
```

大范围导出可按年分片（第一段带表头 `-o`，之后各段不带表头用 `>>` 追加）：

```bash
# 第 1 段（带表头）
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000&max_execution_time=900" \
  --data-binary "SELECT ... WHERE timestamps BETWEEN '2021-06-18' AND '2021-12-31' FORMAT TabSeparatedWithNames" \
  -o daily_all.tsv
# 第 2 段起（把 WithNames 去掉，用 >> 追加）
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000&max_execution_time=900" \
  --data-binary "SELECT ... WHERE timestamps BETWEEN '2022-01-01' AND '2022-12-31' FORMAT TabSeparated" \
  >> daily_all.tsv
```

## 5. 现成命令（可直接复制）

### 5.1 看表结构 / 找表

```bash
# 表结构（ll_stock_daily_sharing 共 74 字段）
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000" \
  --data-binary "DESCRIBE TABLE dws.ll_stock_daily_sharing"

# 某库的表清单
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>" --data-binary "SHOW TABLES FROM dws"

# 跨库找表（⚠️ 必须限定 database，否则会扫到连不上的 MySQL 映射库直接报错）
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>" \
  --data-binary "SELECT database, name, engine FROM system.tables WHERE database IN ('dws','dwd','dim') AND name LIKE '%daily%'"
```

### 5.2 导出日线 —— 复现 `daily_with_maindata_v2.csv`

存成 `export_daily.sql`（46 列，与原 CSV 的 46 列同名同序）：

```sql
SELECT a.code, a.timestamps, a.open, a.close, a.high, a.low, a.vol, a.amount,
       a.ChangePCT, a.TurnoverRate, a.Ifsuspend, a.if_up, a.if_flat, a.if_down,
       a.ema12, a.ema26, a.dif, a.dea, a.macd, a.RSV, a.kdj_k, a.kdj_d, a.kdj_j,
       a.ma5, a.ma20, a.ma4, a.ma8, a.ma12, a.ma16, a.ma47,
       a.market_code, a.category,
       toString(toDate(b.ListedDate)) AS ListedDate, b.ListedSector, b.ListedState,
       a.StockBoard, a.ycp, a.RangePCT, a.RisingUpDays, a.FallingDownDays,
       a.MaxRisingUpDays, a.MaxFallingDownDays, a.HighestPrice, a.LowestPrice,
       a.max_high_9, a.min_low_9
FROM dws.ll_stock_daily_sharing AS a
LEFT JOIN dim.stock_main_info_fd AS b ON a.code = b.SecuCode
WHERE a.category = 'stock'
  AND a.timestamps >= '2021-06-18' AND a.timestamps <= '2026-10-09'
FORMAT TabSeparatedWithNames
```

执行：

```bash
curl -s -u <用户名>:<密码> "<公司ClickHouse地址>/?max_memory_usage=1000000000&max_execution_time=1800" \
  --data-binary @export_daily.sql -o daily_with_maindata_v2.csv
```

注意事项：

- 复现度实测：2021-06-18 ~ 2026-06-16 区间 **5,432 只股票与原主缓存完全一致**；行数 5,998,688 vs 原 5,990,248（差 0.14%，原表导出时可能做过轻微清洗）
- 有约 4% 的股票（230/5432，多为退市/新上市）不在 `stock_main_info_fd` 里，联表后这些行 `ListedDate/Sector/State` 为空——QuantLab 回测只用价量字段，不影响
- 全量约 600 万行，文件预计 1.5~2 GB，约几分钟
- 需要按时间排序时，在 `FORMAT` 前加 `ORDER BY a.timestamps, a.code`（会显著增加内存和耗时，建议配分片使用）

## 7. MySQL 部分

- `/usr/local/mysql/support-files/mysql.server restart` 是**数据库服务器上**的运维命令（Linux init 脚本），在本机执行无效；要 SSH 登录那台服务器并有权限才能跑。它属于服务器运维，和"取数"是两回事
- 本机已装 MySQL 客户端：`C:\Program Files\MySQL\MySQL Server 8.0\bin\`

从本机取 MySQL 数据（需要知道 MySQL 的主机 / 账号）：

```powershell
# 查询并导出制表符文件（--batch 输出制表符分隔）
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -h <主机> -P 3306 -u <用户> -p `
  --default-character-set=utf8mb4 --batch -e "SELECT * FROM 表名 LIMIT 10" <库名> > out.tsv

# 导出整表为 SQL
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysqldump.exe" -h <主机> -u <用户> -p <库名> <表名> > table.sql
```

- `SELECT ... INTO OUTFILE '/path/x.csv'` 是**服务器端写文件**：需要 FILE 权限、受 `secure_file_priv` 限制、文件落在服务器上（本机拿不到），一般不用
- 重要线索：公司 ClickHouse 里挂着指向 MySQL 的映射库（`dps_target` @ <MySQL地址>，用户 <MySQL用户>），2026-10-10 实测**连不上**（ERROR 2002）。说明 MySQL 的数据通常也会同步进 ClickHouse —— **能走 ClickHouse 就优先走 ClickHouse**

## 8. 排错备忘（都是实测踩过的坑）

| 现象 | 原因 | 处理 |
|---|---|---|
| `WHERE type='研报'` 返回 0 行 | Git Bash 命令行里的中文参数被转成 GBK | 改用 `@文件` 方式，或用 `unhex('E7A094E68AA5')` |
| 报 `Connections to mysql failed ... <MySQL地址>` | 查询扫到了连不上的 MySQL 映射库（如 system.tables 不带 database 过滤） | WHERE 里限定 `database IN (...)` |
| Git Bash 里按 Ctrl+Z 后命令卡住 | Ctrl+Z 在 Git Bash 是"挂起进程" | 结束输入用 Ctrl+D；已挂起的用 `fg` 恢复 |
| 查询报内存超限 | 没带内存上限或上限太小 | URL 加 `?max_memory_usage=1000000000&max_execution_time=1800` |
